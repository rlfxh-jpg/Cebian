**建议补进首版的要求**

| 方向 | 需要明确的行为 | 原因 |
| --- | --- | --- |
| 保存不改文件格式 | 读取时识别 UTF-8 BOM、`\n`/`\r\n` 和末尾换行；保存时保留原样 | 否则只改一行也可能让整个文件产生无关差异 |
| 手动重新扫描 | 提供刷新目录操作；监听器丢事件时也定期校验已展开目录 | 文件监听 API 不能保证每个平台、每种编辑器操作都准确推送 |
| 操作期间的状态 | 新建、重命名、删除进行中锁定对应操作；失败后恢复原状态 | 防止连续点击造成重名、重复删除和树状态错乱 |
| 多页面一致性 | 同一扩展同时打开两个工作台页面时，两边都收到变更；服务不为每页重复扫描整个目录 | 这是普通用户很容易遇到的并发场景 |
| 根目录保护 | 根目录本身不能被页面重命名或删除；删除文件夹时展示包含的条目数 | 降低误操作代价 |
| 文件类型边界 | 明确无扩展名文件、隐藏文件、符号链接、非 UTF-8 文件如何显示 | 这些在开发目录中很常见 |
| 配对流程 | 写清本地服务如何首次配对、如何撤销授权、服务重启后是否仍有效 | 目前文档只说“配对凭据”，还不足以实现和验收 |

**最值得做的体验优化**

1. **原生文件夹选择器和最近使用目录。** 输入绝对路径可以作为可靠的首版兜底，但长期使用成本高。由本地服务打开系统选择器，并在页面保留最近使用的目录，会明显改善首次使用和切换工作区的体验。
2. **多文件标签页。** 当前单文件模式下，每次切换文件都可能触发未保存提示。标签页可以让用户同时保留几个编辑状态，但需要为每个标签独立管理版本和冲突，适合首版稳定后加入。
3. **按文件名快速定位。** 大目录树仅靠逐级展开会慢。提供文件名搜索和键盘快速打开，比默认展开大量节点更有效；全文搜索可以留到下一阶段。
4. **忽略规则。** `node_modules`、`.git` 等目录会制造大量监听事件。建议允许用户设置“树中隐藏”和“停止监听”的规则，并清楚区分这两种效果，避免文件只是被隐藏却仍消耗资源。
5. **草稿恢复。** 当前文档明确不保证关闭页面后恢复未保存内容。可以考虑只为未保存文件保存有期限的本地草稿，重开后由用户决定是否恢复；需要同时说明草稿会在扩展存储中留存。

**有特色的创新方向**

- **变化时间线：** 页面边缘提供最近的文件变化记录，能看见“哪个文件何时被外部程序修改”，并点击跳转。它让“实时监听”成为可理解、可追溯的功能，而不只是树节点闪动。
- **外部修改差异视图：** 用户正在编辑时磁盘内容变化，直接展示“我的版本 / 磁盘版本”的差异，再选择重新加载或覆盖。这比一个笼统的冲突提示更能帮助用户作决定。
- **跟随模式：** 用户选中文件后，右侧持续跟随外部写入；适用于日志和生成文件。它应是显式开启的只读模式，并支持暂停跟随、跳到底部。
- **操作预览：** 删除非空目录前列出将受影响的文件数量和部分路径；批量操作将来可以沿用这一机制。

我建议下一版需求文档先吸收**保存格式保留、手动刷新、多页面一致性、根目录保护、配对流程**，这些直接影响正确性。变化时间线和差异视图最能体现这个页面相对普通文件浏览器的价值，但应标为后续阶段，避免首版同时承担太多状态管理。本轮没有修改文档或实现。
